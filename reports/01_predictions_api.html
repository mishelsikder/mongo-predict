Predictions API: a $predict aggregation stage, modelled on $vectorSearch

A prototype of predictions inside MongoDB aggregation pipelines that needs no change to the server: pymongopredict.predictions_api stores a trained model in the database and runs a leading $predict stage on the client. Measured on the 14 MongoDB sample tasks of src/tasks.py and on an Airbnb model with voyage-4-nano.

  • On all 14 tasks a $predict pipeline returns the same predictions as calling the model on the client (regression outputs differ only by float32 rounding between batch sizes: at most 2.0e-03 on zips_population, whose values are in the thousands), so $match, $sort, $group and $merge can be applied to predictions on the server (Sec. 2).
  • The stage costs a median 1.39x the time of the client-side code it replaces, about 57 ms more per 1,000 documents with the hashing embedder: uploading the predictions and the server join take 15% of the pipeline time. Neither depends on the embedding model, so the share is smaller with a slower embedder such as voyage-4-nano.
  • Fitting the default ridge model takes a median 1.7 s per task with 16 threads and default XGBoost 3.2 s; on one thread, 7.5 s against 16.8 s (Sec. 4). XGBoost builds one set of trees per class, so the 39-class task takes it 78 s. Inference is under 11 ms per 1,000 documents for both, far below the time to embed them.
  • A room type model trained with voyage-4-nano on the 5,001 listings outside Porto (holdout accuracy 0.912) labels Porto's 554 listings with accuracy 0.924, through one pipeline (Sec. 3).

1. Design

A $vectorSearch query needs an index created beforehand and referenced by name; the stage must come first and later stages read its score through $meta. $predict keeps that shape (Table 1), with a prediction model in place of the index.

from pymongopredict import PredictionModel, predictions_api
predictions_api.enable()   # pymongo's Collection.aggregate now understands $predict

coll.create_prediction_model(PredictionModel(
    {"target": "room_type", "columns": [...], "embedFields": [...], "embeddingModel": "voyage-4-nano",
     "filter": {"address.market": {"$ne": "Porto"}}},
    name="room_type"))
coll.aggregate([
    {"$predict": {"model": "room_type", "filter": {"address.market": "Porto"}}},
    {"$sort": {"score": {"$meta": "predictScore"}}},
    {"$project": {"name": 1, "predicted": {"$meta": "prediction"}, "score": {"$meta": "predictScore"}}},
])

How a pipeline runs:

  1. Model: create_prediction_model fits a DocumentFeaturizer (columns plus an embedding of the document) and an sklearn estimator (logistic regression or ridge by default) on the documents that have the target, records holdout metrics on 20%, refits on all of them and stores the pickled model with its status in __mongopredict_models.
  2. Client: aggregate fetches the documents selected by the stage's filter and limit, projected to the fields the model reads, featurizes and predicts them in batches, and inserts only {_id, prediction, score, probabilities} rows into a temporary collection.
  3. Server: the rest of the pipeline runs on the temporary collection after a $lookup on _id that brings back each full document; {$meta: ...} references are rewritten to the joined fields and the helper field is removed before the output (or before a final $merge / $out). The temporary collection is dropped afterwards and the result is returned as a list-backed cursor whose stats hold the time of each step.

2. Overhead and agreement on the sample tasks

For each of the 14 tasks (one per sample collection), a model with the task's columns and the hashing embedder on the whole document (no embedding cache) is created on up to 5,000 documents, then applied to up to 5,000 documents four ways: a $predict pipeline that projects the prediction, the client-side code it replaces (find + transform + predict), a $group on the prediction and a $merge of the predictions into a scratch database (Table 2; per task rows in Table 3). Agreement is the share of documents whose $predict output equals the client-side prediction (relative tolerance 1e-5 for regression). The predicted documents overlap the training documents, so the holdout metric, not these predictions, measures accuracy. The $merge wrote every prediction on every task.

4. Estimator fit and inference time: ridge and XGBoost

src/estimator_timing.py featurizes each of the 14 tasks once (the task's columns plus the whole document embedded at 1,024 dimensions, voyage-4-nano's output size; the hashing embedder stands in for it, since fit and inference time depend on the size of the feature matrix, not on where the embedding came from) and then times, on the same train and test matrices, the predictions API's estimator="ridge" (RidgeClassifierCV / RidgeCV over 13 alphas with leave-one-out CV) and XGBClassifier / XGBRegressor with default settings (100 trees per class, depth 6, hist). Fit is timed once and inference (predict, plus class probabilities or scores for classifiers) is the median of 3 runs on the test documents. Both runs share the login node with other jobs; "16 threads" caps BLAS and XGBoost at 16 threads, "1 thread" at one (Table 6; per task in Table 7). Embedding time is not included.

Ridge time grows with the number of training documents (the largest task, grades_exam_score with 80,000 documents, takes 10.8 s with 16 threads), while XGBoost time grows with the number of classes: companies_category has 39 classes and takes 78 s with 16 threads and 361 s with one. With one class or two, or a regression target, XGBoost builds only 100 trees, and it is faster than ridge on 3 of these 6 tasks (grades_exam_score, trips_usertype, zips_population); ridge fits all 13 alphas whatever the number of classes. Going from 1 to 16 threads speeds up fitting a median 4.4x for ridge and 5.3x for XGBoost. routes_codeshare has a single class in its training split, so XGBoost has nothing to fit there. Inference takes 0.9 ms (ridge) and 1.6 ms (XGBoost) per 1,000 documents with 16 threads, 1.6 ms and 11.2 ms with one.

5. Limitations

  • The documents travel to the client and the model runs there; a server stage would avoid that transfer.
  • Results are materialised before they are returned, and the predictions are written to a temporary collection, so the client needs write access to the database.
  • $predict cannot appear inside $lookup, $unionWith or $facet sub-pipelines, and it works from Python only (not from mongosh or other drivers).
  • The stored model is a pickle of at most 15 MB: only users trusted to run code on the client should be able to write __mongopredict_models, unless MONGOPREDICT_MODEL_KEY is set, which signs stored models and refuses unsigned ones.
  • A native stage would follow $vectorSearch: a thin stage in mongod that hands documents to a model service. This prototype fixes the user-facing syntax such a stage could keep.
Computational cost
  • Sec. 2: 1.6 minutes of measured time on the login node's CPUs (MongoDB 7.0.14 on the same machine), no GPU (0 H100 node hours). Throughput of the $predict pipelines: 3,994 documents per second with the hashing embedder.
  • Sec. 4: 18.9 minutes of fit and inference on the login node's CPUs over the 2 thread settings (0 H100 node hours), plus featurizing the 14 tasks with the hashing embedder for each run.
  • Sec. 3: voyage-4-nano embeddings of the 5,555 listings, computed once on one shared H100 (about 2 minutes, under 0.01 H100 node hours) and then read from the embedding cache.
